# Course Creator V3

October 20, 2026. Build one commissioned course through **Asset Creation → Course Creation → Map Creation**, using the [shared workflow](COURSE_WORKFLOW_V3.md), current brief and [focused starter](FOCUSED_CREATOR_THREADS.md). The lead owns the finished player experience. Quality comes first; speed improves by resolving the right question early and avoiding repeated work.

**Blender is the main authoring tool for custom visible course assets and meaningful geometry.** Reuse suitable project or inspected Toolbox assets. Native Studio construction is appropriate for rough studies, simple intentional contacts, gameplay and cases with a clear quality, editability or runtime-cost benefit. Keep custom art sources; tool usage is not a quota.

## Start or resume

Read the latest owner request, applicable AGENTS.md, the compact current record and relevant brief/plan/reference sections. Inspect the intended Studio experience, active course, owner edits and repository/Rojo agreement before mutation. Read actual selected images; use the current phase set and later finish target where relevant. The [Ideation guide](COURSE_IDEATION_WORKFLOW.md) governs the sequential image package; do not recreate it during construction.

Keep a short working contract in the existing course record:

- **Result:** what the player must see and do at this phase's finish, including ordinary obstacles and the complete setting.
- **Preserve:** accepted features, owner edits, movement rules and useful examples.
- **Change:** the current defect or requested improvement, with a before view or reproducible case.
- **Rejected approaches:** fixes the owner has already ruled out.
- **Next proof:** the smallest observation that could show the proposed change is wrong.

Routine construction choices belong to the lead. A request for better arrows does not imply more arrows; a depth effect does not imply removing the floor. Preserve accepted structure when interpreting visual feedback. Use a small reversible comparison for a costly uncertain interpretation; ask only when a material decision remains unresolved.

### Recover the active task

After compaction, interruption or a model change, recover task, phase, current candidate, latest corrections, permissions, manual edits, helper ownership and in-flight operations from the current record. Recheck live facts needed for the next action. Do not replay uncertain uploads, resume a closed course or reset granted permissions. Keep this record editable; freeze a snapshot when a review needs one. Replace stale current facts rather than stacking new current-status headings.

### Plan useful parallel work

Use agents only within this job's authorization. Give each a substantial independent output, owned files and a clear completion check. Start useful source, asset or test preparation while the lead integrates. Reassign finished helpers rather than creating a new agent for each small question.

Explicitly set the authorized model and effort at every spawn, using a context mode that permits those settings. A lead-model change must not silently raise helper effort. Preserve the owner's team, count, independence and threshold. The lead alone controls live Studio/Blender; one writer owns each shared file. Reviewers may request targeted evidence through that controller.

## Blender build method

Follow [saved Blender build guidance](BLENDER_BUILD_WORKFLOW.md): durable builders for substantial/repeated work, scoped rebuilds, useful live inspection and verified imports. Inspect one real imported example before multiplying it. Check actual faces, orientation, scale, pivots, materials and contact joins; matching vertices or bounding boxes alone can miss holes, reversed surfaces and internal overlapping faces. Diagnose a failed import in its source before adding lighting or orientation patches.

## Phase 1 — Asset Creation

**Outcome:** a majority reusable asset kit, cheap whole-route study and finished representative playable section. This is the existing owner critique checkpoint, not an extra approval stage.

1. **Study the whole journey cheaply.** Use actual movement/avatar settings and simple shapes to expose height/section joins, branches, checkpoints, recovery, busy waits and the destination. Include rough masses for large surroundings. Separate movement distance, mechanism waits and recovery allowances. A major mismatch with the race target needs a route decision before broad expansion; recording it as future human tuning is insufficient.
2. **Prove a representative experience.** Include an ordinary obstacle sequence, Normal/Expert choice where present, signature interaction and nearby finished scenery. Choose the most uncertain combination. A beautiful mechanism alone does not establish a good course. Check the weakest ordinary sequence and difficult connection within this study; do not commission multiple full samples.
3. **Resolve the defining qualities.** Use actual imports and ordinary avatar movement. Inspect player-height forward/reverse/underside views, recognizable silhouettes, selected studs/materials, joined scenery, landings, feedback and sound. Compare with the accepted appearance and final-world target. Resolve a central quality gap before repeating the kit; more small props cannot replace missing composition.
4. **Complete useful assets after the direction is resolved.** Define stable names, pivots, front/up, dimensions, mounting contacts and safe scale ranges. Use variants or repeated bays instead of stretching detailed buildings. Group likely editing units and keep moving/gameplay pieces separable. If easy manual editing is waived, retain durable source and recovery without manufacturing per-piece handles.
5. **Import and deliver.** Use the established receipt-bound upload workflow within the granted creator/destination scope. Distinguish export, upload, insertion and correct runtime appearance. Keep editable sources appropriate to each asset, native recovery, IDs/receipts, fit notes, actual sample views and a concise resource/check summary.

Show the rough journey and finished sample together before broad expansion unless that checkpoint is already satisfied or explicitly waived. Complete routine fixes within existing authorization. Proceed to Phase 2 only when authorized.

### Admit assets before multiplying them

Inspect reused assets for geometry/texture cost, collision, editability, provenance and embedded scripts/dependencies. Search a bounded set of promising Toolbox candidates, then choose or author the asset. Keep only deliberately reviewed behavior; do not buy assets or install tools without authorization.

Assign nearby objects a clear role: walkable surface, solid blocker, hazard, safe refuge or decoration. A convincing reachable ledge must support the player or be reshaped so it makes no false promise. Keep visual skins tied to the intended contacts. Use simple collisions where appropriate; hundreds of proxies are not automatically cheaper than one mesh.

## Phase 2 — Course Creation

**Outcome:** a complete playable journey with varied ordinary obstacles, meaningful branches, understandable directions, fair hazards and reliable recovery.

### Build the route and behavior

Establish the final supported selection/start → checkpoint/recovery → lap/finish → exit flow early. Use existing server-authoritative services and repository/Rojo source. Label any preview's bypasses; preview success cannot close the corresponding shared-flow requirement. Course work does not authorize unrelated economy, DataStore, purchase or remote-security redesign.

Give every section a deliberate player-action sequence, not just a theme or platform count. Build the route, ordinary obstacles and signature encounters together. Check joins, actual takeoff support, headroom, camera space, passing/waiting pockets and rough surrounding masses before final scenery.

### Prove the challenge and the boundaries

For each branch, state the skill demand, shared fork/rejoin, retained encounters, reward and failure cost. Compare routes from the same endpoints under comparable movement and hazard conditions. Separate travel from waits and test-driver settling. Narrow platforms alone do not establish interesting difficulty; a recorded finish cannot close repeated feedback that Expert is easy or unrewarding.

Try the shortcuts a player would notice: straight walks, diagonal and downward jumps, neighboring lanes, catch returns, scenery/supports, early boarding/exit and skipped checkpoint/hazard relationships. Start from the observed temptation rather than only following the prescribed route. Repair layout when needed; do not add a wall or equivalent blocker when the owner rejected that approach.

Cover every supported branch's entry, rejoin and next checkpoint. After route/progression changes, obtain continuous ordinary-movement completion through the supported race flow, required laps and legitimate finish. Normally a full Normal run and a full Expert run can cover independent choices, with focused branch/rejoin checks. Run additional mixed combinations when choices affect shared state, previous results reveal an interaction or the owner explicitly requires them. Do not automatically multiply independent branches into every possible full race.

Check the finish as players approach it, including a reasonable jump or off-center crossing when the visible destination permits those actions. A sequence of teleported checkpoint placements proves only those isolated checks.

For changed mechanisms, cover the full travel space, visible warning, safe wait, early/late crossing windows, actual contact, recovery and relevant reset/restart behavior. Contact must match the visible danger without hidden padding; keep resets and return motion fair. Sample different arrivals and a leader/follower case when shared timing matters. Preserve every required signature's presence, operation and actual encounter on the intended routes. Use the current agreed danger language; falling recovery and on-course obstacles have different jobs.

Use geometry, landmarks and sparse cues for navigation. Inspect a fork before reading its explanation: the Normal entry, Expert commitment and next landing must be understandable. Add signs/arrows where they resolve a real choice, rather than repeating them at every landing.

## Phase 3 — Map Creation

**Outcome:** the commissioned finished world, with coherent composition at player height and a satisfying destination.

### Compose the environment around the actual route

Preserve accepted gameplay while completing close scenery, section transitions, supporting masses, foreground/middle/background layers, sky/horizon and final lighting. Compare the whole installed composition and each section's weakest view with the selected target. A polished landmark does not compensate for unfinished surrounding spans. Prefer connected architectural or natural groups over uniform filler.

Preserve the requested medium: sky textures, physical scenery, an atmospheric veil and a presentation backdrop are different outputs. Do not remove accepted floor or structures merely to create an effect. Keep props, shell ends, roofs, terrain and support joins convincing from accessible views, including falling/reverse views. Intentional floating obstacles remain valid when they belong to the accepted design.

Recheck affected contact, jump/camera clearance, misleading surfaces and shortcuts after art changes. Course-specific ambience uses the existing lifecycle; verify relevant entry, exit and restoration without changing unrelated lighting. Do not rerun unchanged movement suites for an inert cosmetic patch.

## Practices across all three phases

### Preserve edits and keep the result practical to tune

Before risky replacement, capture a recoverable native/source baseline and inspect current owner changes. Patch the intended groups. Move a gameplay unit with its skins, contacts, supports and dependent checkpoint/respawn relationships. Never replay an old whole-map installer over newer work.

Keep the active candidate, necessary comparison and current recovery identifiable. Verify older native files and their restore paths before removing live copies; existing-root deletion or relocation still requires its applicable authorization. Avoid archives containing older archives. Moving history to ServerStorage organizes it but does not remove its stored memory cost.

Keep one concise current record and detailed recipes/logs in files. Freeze changed outputs and the dependencies needed to identify the reviewed candidate; link historical evidence without repeatedly copying or hashing all old reports and unrelated sources. Verify the preservation boundary appropriate to the actual mutation.

### Optimize while preserving the experience

Optimize while the sample is small and as dense assemblies grow. Track placed/unique meshes, textures, triangles, collisions, transparency, lights and recurring mechanism work separately. Reuse compatible asset IDs and simplify unseen detail. Keep useful editability unless waived; avoid merging unrelated gameplay pieces or making every trim a runtime object.

Use matched views and relevant movement to protect the agreed composition, color, challenge and finish. Report costs that increased as well as decreased. Measure actual rendering/physics/script/memory/loading cost where useful and available, identifying scenario, device and player count. Inventory reductions, static occupants and device emulation do not establish FPS or real twenty-player performance. Do not invent a device/FPS gate when none was commissioned or change global settings speculatively. See [Roblox performance guidance](https://create.roblox.com/docs/performance-optimization/improve).

## Proportional verification and evidence

Before running a check, name the requirement or regression risk it answers. Validate a small test setup before a long run. Test the failed section first; distinguish setup/observer/assertion failures from actual game defects. Repair the test only when evidence shows it is wrong, retain failed results and never weaken a valid guard to obtain a pass.

| Change | Required focus |
| --- | --- |
| Art/material/detail only | Current affected native views, imported surface/neighbor joins, visible route information and resource change. Check moving-camera rendering for flashing. |
| Placement, collision or branch | Actual affected jumps/contacts, head/camera space, tempting bypasses, checkpoint/rejoin relationships and directly affected completion flow. |
| Hazard timing or contact | Warning, full cycle, safe waits, actual hit/recovery and relevant follower/reset behavior. |
| Shared runtime or lifecycle | Supported entry/exit, recovery, restart/character changes and affected branches in a fresh installed-source Play session. |
| Defining sound/feedback | Actual playback or representative recording paired with the interaction. Loading alone does not prove audibility or quality. |
| Preservation/recovery | Intended changed scope, important unchanged properties, current source/native identity and a usable restore path. |

Reuse demonstrably unchanged evidence. Broaden checks for an actual shared dependency, failure, unknown risk or explicit owner requirement. Do not build a new test framework, reproduce every historical case or demand byte-identical unrelated content for a narrow cosmetic fix. If test setup or capture recovery becomes the main work, stop expanding it and choose the smallest supported way to answer the remaining required question.

Mark requirements verified, failed, unavailable or owner taste pending. Required missing proof remains pending; optional future device/crowd work does not become a surprise blocker. Static measurements cannot replace required native appearance or motion evidence.

### Review the experience before assigning scores

Before involving the requested reviewers, the lead inspects the whole course and closes obvious missing requirements. Prepare one compact packet: current brief/owner corrections, accepted comparison, installed candidate, useful native views/movement evidence, actual changes and remaining questions.

Reviewers first derive success from the brief and inspect the actual result, then consult the builder's explanations and technical receipts. Each challenges a consequential assumption in their area. They can request a fresh angle, alternate approach or raw result through the sole controller. Matching hashes establish identity; the lead can provide the shared identity check instead of every specialist repeating the entire preservation audit.

A known core gap in difficulty, navigation, completeness or the selected visual identity is a material finding, even when scripts work. An open owner complaint keeps its original scope until matched before/after evidence or changed player actions answer it, or the owner changes the requirement. Do not rename it minor polish to clear a score threshold. Missing required visual evidence receives a hold/unverified judgment, not an invented visual score. Subjective human timing and taste remain distinct, while the lead still makes a reasoned quality judgment against the agreed target.

Retain the owner's independent reviewer count, roles and thresholds. Keep implementation authors separate from their final judges. Consolidate findings, make a real correction and return affected work to the same judges. Each confirms their own final scope, with explicit unchanged-area reuse where justified. Do not average, replace a critical reviewer or pressure scores. A new candidate does not automatically require a second full team or every test again.

If the same owner complaint returns, revisit the interpretation, design or diagnostic method before another similar patch. Continue while making measurable progress; do not impose an arbitrary iteration timer or chase a score through inconsequential changes.

## Chrrxs, official Studio MCP and Rojo

Use [connection guidance](ROBLOX_MCP_SETUP.md) and tools actually available. Verify the intended place and canonical paths. Repository/Rojo is durable for scripts; native geometry needs its own recovery. Read running module state through runtime tools, not a separate plugin-context module cache.

Keep one intended authoring Studio and one lead-owned test session. Use native multiplayer clients only for a relevant authorized check; do not open accumulating authoring/test copies to escape a stalled command. Preserve another user's session. Restore camera/FOV/type, device/network/lighting and test state after success or failure; stop only owned or authorized sessions.

Prefer supported APIs, CLI and background work. Respect desktop-use restrictions. For blank captures, check one concrete cause and try a bounded supported alternative. Keep the known limitation in the current record; another attempt needs a changed condition or a distinct diagnostic. Do not repeatedly ask the owner the same visibility question or seize desktop focus.

After a mutation timeout, inspect its operation status, receipt and live result before retrying, including through another connection. An unknown outcome is not proof of failure. Preserve pending uploads and use their receipts. Do not install or reconfigure tools during a course without the needed scope. If automatic approval review blocks an action, explain the real reason and continue other authorized work; do not bypass the rejection.

## Close the phase

Deliver the actual installed candidate, useful before/after views, concise changes and checks, exact source/native/recovery paths and the remaining owner decision. Say **ready to test in Studio** when installed; separately state whole-place Save and publication status so “unpublished” does not imply untestable.

Reconcile the current record with the installed result and latest owner instruction. Keep historical reports immutable and current status outside their frozen inputs. Continue into an already authorized next phase after its real checkpoints; otherwise stop at the commissioned boundary. Explicit owner acceptance closes the job while retaining unperformed-test limits as facts. Further work on an accepted course needs a new request.
