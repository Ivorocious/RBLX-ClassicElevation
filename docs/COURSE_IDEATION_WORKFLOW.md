# Course Ideation V3

Use [the shared V3 workflow](COURSE_WORKFLOW_V3.md) and [ImageGen prompt recipes](COURSE_IMAGEGEN_PROMPTS.md). Continue in the same general Course Ideation chat; keep completed courses and their decisions as history. Produce a complete, consistent package, then create a fresh focused creator for the commissioned course using the [shared starter template](FOCUSED_CREATOR_THREADS.md). The owner should not need to copy a handoff or reconstruct the intent.

V3 is the standing default; the owner does not need to name it. The October 9, 2026 sequence is **Phase 0 — Course Blueprint**, then reference development for **Asset Creation → Course Creation → Map Creation**, one phase at a time. Each phase starts with one image, receives owner amendments, then expands to its selected set: Phase 1 has 2–10 images; Phases 2 and 3 have 4–6 each, including the refined first image. Retain the active course's accepted decisions, permissions and owner-selected agent arrangement across follow-ups unless changed. Do not copy a completed course's team or approvals into a new course.

## Start from the new idea

Develop the owner's rough idea through concise, natural back-and-forth. Propose a coherent direction and make useful routine choices. Ask only for missing decisions that materially affect the course. Do not ask the owner to repeat something already decided or turn the process into a questionnaire.

If the owner wants options without a theme, offer a few distinctly different experiences: each needs a recognizable setting, a signature player action and a different visual identity. Recommend one and explain the practical difference. Use the number of alternatives requested; otherwise keep the choice small. If the owner is confused, show clearer differences rather than adding more options or lore. Once a direction is selected, carry routine design choices through the full requested run without repeated “next” prompts.

Carry forward the owner's design principles: immersive player views, close but readable surroundings, compact lively racing, distinct sections, meaningful obstacles, fair information, useful manual editability and a rewarding destination. Do not carry forward a previous course's theme, section/shortcut counts, hazards, landmarks, dimensions or timings as a fixed template. Choose stud treatment from this course's accepted direction.

Use the owner's game-wide targets: 20 racers, compact competitive spacing, 4–6 minute whole-race completion for average players and 2–3 minutes for experts. Keep each course's format and lap count explicit. Section budgets and physical dimensions remain proposals until measured.

Inspect relevant existing systems and assets read-only when that changes feasibility. Do not start building a course, launch tests, alter Studio, or reset Blender while ideating. Owner examples establish the requested presentation or appearance only where stated; a square garden showcase does not impose its footprint, theme or objects on the next course.

## Develop an evolving course brief

Keep accepted decisions, proposed details and unresolved assumptions distinct. Do not prematurely label the entire plan approved because the owner liked its initial direction.

Develop these connected pieces:

- **Experience:** player fantasy, setting, start, destination, course form, intended capacity, normal difficulty and target devices.
- **Journey:** ordered sections with a distinct purpose, landmark, spatial character, transition and pacing role.
- **Player actions:** a concrete ordinary obstacle sequence for every section, alongside signature hazards, movement choices and deliberate rest. Describe what the player reads, aims, times or changes direction around; a platform list or impressive mechanism cannot stand in for the surrounding course.
- **Branches:** difficulty before commitment, entry/rejoin, required checkpoint state after the merge and eventual race completion, meaningful time/distance savings and recovery. For each normal/expert pair, state the actual difference in precision, direction, height, commitment or timing. A shorter copy of an easy platform line is insufficient. Decide whether each shortcut bypasses a signature encounter or challenges it differently; avoid accidental scenery bypasses.
- **Risk and recovery:** checkpoint triggers and readable visual treatment, safe waiting, failure results and retry cost. Avoid automatic checkpoints at every landmark or a trivial checkpoint immediately before the finish unless the design calls for it.
- **Timing:** distinguish skill, familiarity, chosen route, falls and hazard waiting. Compare shortcut savings for the same player skill. Durations and jump dimensions remain targets until tested.
- **Visual identity:** recognizable silhouettes, palette, stud/material treatment, scale, connected scenery at player height, sky/horizon, lighting, section contrast and an earned finish. Choose what must survive optimization; identify whether environment references mean sky imagery, physical scenery, lighting/effects or presentation only, preserving the owner’s requested output type. Use deliberate openings and substantial grouped forms instead of uniform filler.
- **Production scope:** Blender is the main authoring tool for custom visible course geometry; identify suitable project/Toolbox reuse and intentional native contacts. Name the existing race/entry flow, preview limits, necessary new behavior, owner tuning needs and exclusions. Creator checks integration early in Phase 2. Do not commission a separate game framework or leave ordinary obstacle design for the owner.

Use stable section/checkpoint/shortcut/hazard/landmark IDs when useful. These support the plan; they are not automatically text for the game world. Let route shape and landmarks guide movement; reserve signs for ambiguous choices and information such as hazard state or timing.

For moving hazards, describe visible approach or supports, warnings, steady or bounded motion, the complete travel area, safe waits, usable windows, hit outcome, recovery, exit and reset. Do not rely on random timing that can remove every safe window. Distinguish a safe perch from a checkpoint. Do not promise actual reachability, clearance, fun or performance from a plan.

Keep room for compact competitive flow: selected passing places, brief narrow stretches and safe merges/respawns. Do not widen every surface to the full racer count. Balance surrounding density with clear landing and hazard information; leave deliberate openings.

Write one compact section table: ordinary action sequence, Normal difficulty, Expert demand/reward, local visual identity, recovery and the question Creator must prove. Choose a representative section that exposes both a signature and the weakest uncertain ordinary sequence/branch. Include defining sound, feedback and avatar scale where relevant. Keep the rough whole-route pacing/space study beside it. A strong mechanism sample must not conceal an unresolved journey; images cannot prove dimensions or playability.

Check the journey as a whole: give sections a deliberate rhythm of introduction, variation, harder combinations, recovery and payoff where appropriate. Repeated jumps should have a purpose; changing the scenery alone does not create new gameplay. Give each section one memorable player moment. Allocate rough travel/wait/recovery time shares and reconcile their total with the stated race/lap target, labeling all estimates. State which takes priority if duration conflicts with preserving encounters. Check the combined shortcuts against the whole experience: name what both routes must retain and what may be bypassed. Revisit that priority before a broad timing revision. Flag uncertain transitions or bottlenecks for Creator's simple full-route study alongside the finished representative section. This uses the existing brief and diagram, not another mandatory document or owner approval.

When a consequential choice is unresolved, compare a few inexpensive layout/action sketches and choose using the brief's goals before commissioning final imagery or asset families. Do not generate multiple full packages to settle one local question. Leave enough freedom for Creator to fix tested fit problems while preserving accepted intent; flag any material route/design departure for the owner.

## Calibrate the intended detail early

The current default is **polished stylized detail**, richer than Shipwreck's rejected bare low-poly pass. Use substantial silhouettes, selective curved edges and trim, believable natural layering, fuller foliage and readable material variation. Give landmarks and nearby course surfaces enough form to feel finished; use simpler distant forms that still belong to the same world. Do not drift into microscopic realism or use plain low-poly blocks as a universal performance strategy.

State three concrete visible qualities that the finished map must preserve, alongside the intended device/player targets. Link the selected examples or accepted native sample and preserve the specific owner preferences they demonstrate. For example, describe a naturally enclosed cave and varied rock silhouette, not just “higher polygon count.” The style is an appearance target; Creator sets and checks actual resource budgets. No image establishes a safe triangle count or mobile performance.

Calibrate recognizable assets, nearby surroundings and the sky/lighting mood in the first Phase 1 reference and finished-sample target before expanding that phase's images. Carry those choices into the later phase references. A quiet showcase background can remain; record the intended in-game atmosphere in the brief. Extra sky or detail studies are optional for unresolved choices. Phase 1's completed sample already demonstrates the intended final quality; Phase 3 develops the finished world around the same course. Use the latest owner-selected direction. If a material style choice is unresolved, present that choice while continuing independent planning. When the owner changes detail, revise the brief, affected phase references and any existing creator starter together.

## Phase 0 — Course Blueprint

Make the whole course understandable before detailed Phase 1 imagery. Use the evolving brief and native diagram to place the journey, height changes, signature encounters, Normal/Expert choices, recovery and passing/boarding spaces. Allocate provisional movement, waiting and recovery time against the whole-race targets, then identify the required asset families. Review consequential proposals naturally with the owner before committing them to the first phase reference.

Phase 0 may use a route-flow view and a spatial/height view, chosen for the course. Add a simple 3D overview only when it resolves a named uncertainty. This is a planning stage; the cheap playable whole-route study still belongs to the commissioned Phase 1 build. A diagram or concept does not establish actual clearances, race time or 20-player capacity.

Create a real editable `.drawio` file in the course folder using native shapes and connectors. The owner should not need to position shapes, paste diagram code or repair the file. Use draw.io MCP when available, or generate the native file directly and validate it.

Choose the course form from its intended experience, height, journey and pacing before framing any images. Winding, vertical, branching, cliffside, island-chain, looped and compact forms are all valid; there is no default square base or rectangular enclosure. Orthographic/isometric describes the camera presentation, not the required footprint.

Show start/finish, section order, main/expert paths, branches and merges, checkpoints, safe areas, signature hazards, major landmarks and useful environmental relationships. Use route-flow and spatial/relative-height views as needed. Do not force a two-page count or a City Run-shaped layout onto every course.

Label schematic layouts as not to scale. Identify what dimensions/elevations are agreed targets versus measured constraints. Use a consistent orientation, route colors and legend across the native plan and later map-image prompts. Keep important routes legible rather than buried beneath decoration.

Provide readable deterministic previews of the native plan for inspection and for ImageGen input. Inspect renders when available and validate connector references. Say whether the preview came from draw.io or from shared generator data; do not claim editor rendering was checked when it was not. Preserve manual diagram edits before regeneration.

Present the brief and diagram together for refinement. Resolve settled choices in the files without imposing an extra formal approval ceremony.

## Develop one phase's references at a time

The default flow is **Phase 0 blueprint → Phase 1 first reference → owner amendments → Phase 1 selected set → Phase 2 first reference → owner amendments → Phase 2 selected set → Phase 3 first reference → owner amendments → Phase 3 selected set → consistency review → create the focused Creator for commissioned work**. Generate only the current phase's first reference initially. Complete its normal review and useful supporting references before starting the next phase. The three phase designs depict successive intended results of one course; do not generate all three masters together.

| Starting concept | What it shows |
| --- | --- |
| **Phase 1 — Asset Creation** | Reusable asset families and one finished playable sample, with the wider course kept as a rough outline. Show enough context to judge scale, shape, detail and how the pieces work together; a showcase cannot prove the kit is complete or usable. |
| **Phase 2 — Course Creation** | The complete course: obstacles, branches, checkpoints, warnings, passing and recovery spaces, plus rough large surroundings. Route-facing assets retain the intended quality; the surrounding world is still being finished. |
| **Phase 3 — Map Creation** | The same course with its finished surroundings, atmosphere, layers, transitions, landmarks and destination. Preserve route relationships and visible hazard/recovery information. |

Use **ChatGPT ImageGen** for concept imagery. Begin with an isometric-style 3D showcase using an orthographic camera, clean framing and a quiet background. Keep the same plan revision, world orientation, avatar scale and appearance language across phases. Reuse the first camera where practical so changes between stages are easy to compare; let Phase 1's kit/sample framing reflect its actual deliverable. Adapt framing to the course shape without stretching or flattening the design.

Save fully expanded, ready-to-paste prompts in `VISUAL_INSPIRATION_PROMPTS.md` using the [phase recipes](COURSE_IMAGEGEN_PROMPTS.md). State which input is the layout authority, phase edit target or appearance reference. Inputs can include the owner's selected examples and the native plan preview. Do not assume every attachment is an edit target.

## Iterate the selected phase designs

Settle course form, route relationships, scale, visual identity, surrounding density and the destination before making the extra angles. Use targeted edits and restate the details that must remain. Keep one selected master concept per phase and mark earlier versions as history. Check Phase 1's finished sample against the Phase 3 quality target; show rough masses for large surroundings in Phase 2 so the final art does not unexpectedly consume route or camera space.

Each phase needs a short completion description in the existing brief: required result, what remains for later phases, visible qualities to preserve, Creator's allowed design freedom and the checks that imagery cannot prove. The native diagram governs connections and order; the brief governs requirements; images guide appearance. Resolve contradictory landmarks, routes, heights or stage content before calling a design settled. When a visual revision changes an accepted functional decision, update the brief and diagram as well.

This is the owner's normal design iteration, not an approval ceremony for every image. Preserve feedback and permission already given. Generate only affected replacements; do not rerun all phases for a local planting or material change.

## Expand the reviewed phase with purposeful references

After the current phase's first design is reviewed and amended, expand to **2–10 selected images for Phase 1**, **4–6 for Phase 2**, and **4–6 for Phase 3**. These are final totals per phase, including the selected first image, usually view A. Drafts and replaced versions do not increase the count. Choose the number by useful coverage; ten is available for Phase 1, not automatically required. Do not make tiny collages or regenerate view A just to satisfy a count. If a shared-scene set replaces concept angles, retain the approved ImageGen master separately as the appearance target and record the reason and counting.

Give each supporting image a specific job. Phase 1 can need asset-family detail, a mechanism assembly, an operating-position study or the finished sample at player height. Phases 2 and 3 can need overview, reverse, cutaway and player views that expose connections or hidden areas. Do not default to four diagonal camera rotations. Record each purpose, view and world orientation in the index. Reuse corresponding cameras, scale and lighting across phases where useful; explain intentional framing changes. Preserve the design rather than mirroring or rearranging objects to improve a view.

Generate each additional concept view using its selected phase master, the relevant native-plan preview and only the other references it needs. Recheck section order, branches, checkpoint/hazard locations, landmark positions, relative heights, asset identity and hidden connections. Correct or reject an attractive wrong angle. A direction to preserve the layout in a prompt does not establish that the generated result did so.

For exact matching geometry, render all angles from one shared 3D scene with fixed geometry, materials and world lighting. Reuse a suitable existing scene when available. Label these as reconstruction/reference renders and retain the selected ImageGen appearance target; a reconstruction may simplify or omit pictured detail. Building a substantial model solely for Ideation images is separate work, not an automatic prerequisite. Do not claim ImageGen created a real orthographic projection of a recovered 3D model or that any reference render is Studio evidence.

## Keep the package useful

Mood boards and extra clay studies are optional for a specific unresolved question. Name the question before adding one; do not recreate the previous mandatory package. A full Ideation run develops and inspects each phase's selected reference set in sequence, with the owner's amendment pass between its first image and expansion. Supporting images do not each require a new permission prompt. Respect a request limited to Phase 0, one image, prompts or another partial study and mark later generation/review pending. This workflow does not commission a build.

Keep ordinary showcases free of IDs, labels, slogans, software interfaces and HUD unless requested. Use the native plan and external captions for precise labels. Prompts should describe intended use, phase content, subject, camera, spatial facts, avatar scale, materials/light and accepted details that must remain. Keep fixed route facts separate from artistic freedom; do not paste the entire implementation brief into every prompt.

A concept's simplified masses do not lower the selected finish quality. A rich image does not require every tiny decorative feature to become geometry. Review silhouette, near/middle/far density, material language and readable landing/hazard information. The course form determines the footprint; the image composition adapts to it.

Creator compares actual phase milestones with the corresponding references and inspects normal player-height views, including relevant reverse/underside angles. The overhead package does not prove camera comfort, traversability, timing, difficulty, intended racer capacity or device performance. Keep the early playable sample and real checks in all three phases; do not substitute more generated images for missing build evidence.

## Handle revisions without losing decisions

For a late obstacle, aesthetic or capacity change, check affected section sequences, branches, checkpoints, recovery, asset needs, warnings, timing budgets and visuals. Update the brief, native diagram and affected prompts together. Mark generated images stale if they no longer match. Regenerate only affected images when image generation is authorized.

Treat owner edits and feedback as new evidence. Keep the exact comparison: what works, what changes and why, plus previously rejected approaches. Preserve accepted features outside that change. Better arrows need clearer decisions, not automatically more markers; atmosphere or depth does not automatically remove a floor or change the route. State consequential inference plainly and resolve it through a small reversible comparison or a necessary owner decision. Newer explicit directions govern.

For an image-review-only request, inspect and explain; do not implement changes. Distinguish attractive appearance from unclear route geometry, missing traversal surfaces, excessive labels, unrealistic detail, weak hazard coverage or missing destination reward.

## Finish by creating the focused Creator chat

The course folder should normally contain:

- `COURSE_BRIEF.md`: current specification, decision status, sections/obstacles, constraints, targets, asset needs and latest changes.
- A native `.drawio` plan and its readable previews.
- `VISUAL_INSPIRATION_PROMPTS.md`: fully expanded prompts for generated current-phase references and revisions, plus the phase/view/purpose index. Identify later phases as pending rather than generating their images early.
- Selected phase-reference images for a completed full run: Phase 1 has 2–10; Phases 2 and 3 have 4–6 each, including each selected master, with local project paths and matching revisions. Identify any partial or prompts-only delivery explicitly.
- `CREATOR_START.md`: the fully filled first message using the [shared template and course block](FOCUSED_CREATOR_THREADS.md#first-message-template).
- One compact current-state record, reusing the existing brief/status file or `CURRENT_STATE.md`.

Do not add a redundant obstacle document. Reuse existing project conventions rather than creating another management system.

The image index identifies phase, view/camera, filename, source type (ImageGen concept, shared-scene reconstruction or actual Studio image), selected master, accepted/proposed status, compatible brief/layout/visual revision and any known discrepancy. Keep master appearance targets explicit when a reconstruction is also used. If only prompts were requested, mark images not yet generated; prompts alone do not establish a completed set or accepted appearance.

Before creation, reconcile late instructions into the actual files. Confirm all three phase completion targets, the selected-reference index, section IDs/order, branch connections, signature-hazard rules, checkpoint recovery, capacity, duration definitions and visual anchors agree across the package. Check the package's actual images and their purposes, not just the count. Mention unresolved choices that materially affect construction; routine build details can be delegated to Creator.

Record brief, layout and visual revisions and their compatibility. Remove active wording that contradicts the selected detail level or asset-source policy. Open the named files and inspect the selected images before calling the package ready. Creator should be able to read local files directly; do not make the owner attach every image again when the task has access to the exact saved paths.

The Creator prompt carries the course identity, authorized phase/result, exact current input paths, accepted examples, preservation/rejected approaches, representative-section checkpoint and actual helper/reviewer authorization. Link the brief, reference index and canonical Creator checks; do not paste the whole brief, every image path and a second test handbook into the starter. Keep required evidence distinct from optional future checks. Retain the current job's settings on follow-ups and the shared recovery rules; never inherit a completed course's team or scores.

Always carry performance priorities into that prompt: intended player count, mobile/lower-end accessibility, any agreed resource or runtime targets, and the player-facing visual qualities that optimization must preserve. Mark numerical targets still undecided; do not imply that a style or image has established acceptable runtime performance.

Follow the [creation procedure](FOCUSED_CREATOR_THREADS.md#ideation-prepare-and-create): resolve the local project, create `Course Creator — <course>` with the filled first message, save its identity in the course record, and confirm it starts the correct authorized task. The owner's standing instruction covers this creation step for commissioned work; a brief-only or review-only request does not start a build. Use the standing Course Creator default explicitly: `gpt-6.1-sol` with `thinking: max`, unless the owner has selected another model for this course. Carry authorized helper/reviewer settings separately; this model default does not authorize a team.

When separately authorized to follow or review Creator, use the existing candidate and one consolidated findings list. Judge the owner’s actual experience requirements; do not duplicate its implementation or commission another full review team unless requested. Coordinate Studio ownership and communicate only within the owner’s messaging authority.

Report the created chat and actual startup state, then return Course Ideation to standby. Related revisions remain in that course's creator; the next course gets a fresh creator. Preserve existing active work in place unless the owner requests a transfer. Existing files named `COURSE_CREATOR_HANDOFF.md` remain valid source/history where applicable, but no longer direct new work into a general creator chat.
