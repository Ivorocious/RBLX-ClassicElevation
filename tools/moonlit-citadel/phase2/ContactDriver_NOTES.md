# R04 native contact driver

The two scripts automate the existing ContactCases arm/readiness/evidence flow inside the lead-owned native Play session. They are new test-only sources. They have passed Lune parsing; the lead must install and run them to establish native behavior. No Studio connection was used by this helper.

Install `ContactDriver.server.luau` as a disabled Script in ServerScriptService. For an existing native session, create a disabled client LocalScript template in ReplicatedStorage, then clone it into each actual local PlayerScripts through the client runtime. PlayerScripts does not exist on the server; do not wait for it there. StarterPlayerScripts is also suitable before launching. Set `RunContactDriver=true` on all three executable copies, then enable both client copies and the server within the client's 60-second transport-discovery window. The server waits at most 30 seconds for both handshakes. Require unpublished Studio place/universe zero, exactly native Players -1/-2, current active `Workspace.RaceCourse` candidate `MC_P2_C01_R04`, and inactive ClientProbe/ClientSuite on both clients. Complete actual lobby arrival first. Keep the existing ServerProbe running: it supplies the real `MCPhase2Progress` observer bridge; the driver never writes that bridge or credits progress.

The default fixed plan has 26 cases: four 16-second adjacent cases (Lower/Upper × bays 1/2); overhead and side for each stage/bay with both affected-user orders; one native red-body positive selected from actual visible Neon/MoonlitHazard/VisibleResetContact parts; three distinct SwingBand1/2/3 cage-body positives; and light/accessory negatives on SwingBand1. The default negative stand is the actual `Obstacles/Gallery/NormalWaitBefore1/Contact` center with local offset zero, confirmed from Layout.gallerySurface's `Gallery` group. Existing ContactCases must prove body overlap zero and actual light exposure/accessory overlap. A center without the required evidence fails; the driver does not infer safety or retry another position.

Optional server attribute `CaseNamesJSON` selects a bounded subset of those fixed names, for example `["Adjacent_Lower1"]` for initial installation testing. Names are `Adjacent_Lower1/2`, `Adjacent_Upper1/2`, `overhead_Lower1_Actor1/2` (and equivalent stages/bays), `side_Lower1_Actor1/2` (and equivalent stages/bays), `RedBody`, `CageBody1/2/3`, `light-miss`, `accessory-miss`. A subset proves only its selected cases.

For a separately measured negative location, optional `NegativePlanJSON` accepts one or two entries such as `[{"case":"light-miss","measuredSafeStand":true,"targetPath":"Obstacles/SwingLanterns/SwingBand1","standPath":"Obstacles/Gallery/NormalWaitBefore1/Contact","standOffset":[0,0,0]}]`. Only light/accessory negatives are configurable. The contact must exist and be collidable/MCWalkable; the finite local horizontal offset stays within its actual size. The actual body-clearance/exposure assertions still come from unmodified ContactCases. This explicit plan is an operator measurement assertion, not geometric evidence by itself. No red-adjacent miss case exists in the current ContactCases API; the lead handles that separately.

Before each case the server calls `TrialControl.Services()` and `Restart()` and waits at most 35 seconds for a different real shared race with both actual racers Racing, official, staged, CP0/f0. The normal shared unload/reload is allowed only during that bounded restart wait. `ContactCases.Start()` owns placement and temporary blockers/accessory creation. Clients call `ObserveClient()` only, with no movement or prediction. For lifts, actual fresh `Readiness()` pairs call `Begin()`. At `AwaitingClientEvidence`, exact `EvidenceSlice(measurementStartedAt, measurementEndedAt)` pairs call `SubmitClientEvidence()`, retaining the original foot-gap, relative-pose, coverage and gap checks. For hazards, the same exact slices are retained as supplemental native observations; ContactCases' paired Deck-support validator applies only to lift cases. Hazard observers use Lower Bay1 as a recorded relative-coordinate reference, not as their expected support or as a ride claim.

The uniquely owned RemoteEvent is under ReplicatedStorage/Remotes. Both directions bind protocol, owner, case nonce, case ID, race ID and candidate; the server also binds the actual Player caller and declared user ID. Evidence is exact JSON in ordered chunks up to 16,000 bytes, with a 900,000-byte raw cap and the existing sub-95,000-byte slice cap. Oversized or malformed evidence fails; no truncation/downsampling occurs. Slices are sent first, within the original 25-second evidence window; complete raw observer reports follow separately. Client originals are retained locally before transfer, including failures.

Read server Script attributes `DriverState` and `DriverEvidencePath`, or its evidence folder's compact `StatusJSON`, without collecting large reports through serial client VM evaluations. Server evidence lives under `ServerStorage.MoonlitPhase2Evidence/MC_P2_C01_R04_ContactDriver_<guid>/Case_<index>_<name>/`: `ServerRaw`, `Client1/2ExactSlice`, `Client1/2Raw`, plus original failure snapshots/transport buffers when applicable. The suite has `SuiteRaw`. Client originals live under each PlayerScripts folder with that same owner name. Each retained report folder declares JSONChunks/JSONBytes and stores `JSON_001` onward, at most 60,000 bytes each; retrieve one chunk at a time and concatenate in order. Existing ContactCases' own native case folders remain intact.

One failure stops the suite and retains the report before owned cancellation. Set the server Script's `StopContactDriver=true` to request a bounded stop. The driver leaves the real race and players in their actual last state and keeps its marked inactive transport/evidence for inspection. No shared race-end action or unrelated deletion occurs. Any later cleanup must verify `CreatedBy=MoonlitContactDriver1` and the exact DriverOwner before removing driver-owned objects. Existing ContactCases cleans only its own marked temporary blocker/accessory.
